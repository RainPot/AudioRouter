# macOS 多设备音频输出 App 技术方案（重实现路线）

## 1. 当前结论

当前工程已经验证过两条实现路线：

- 路线 A：`Process Tap -> AVSampleBufferAudioRenderer`
- 路线 B：`Aggregate Device + 系统默认输出切换 + 硬件音量`

这两条路线都不能稳定满足最终目标：

- 多个物理设备稳定同时输出
- 每个设备独立音量控制

当前真实结论是：

- 路线 A 在当前形态下无法稳定让多个物理设备都进入可播放状态
- 路线 B 可以部分借助系统聚合输出，但独立音量严重依赖硬件能力，不符合产品目标

因此，本项目进入 **真正重实现路线**。

## 2. 重实现目标

### 2.1 最终目标

做一个 `macOS 14.2+` 菜单栏 App，支持：

- 同时选择多个物理输出设备
- 每个设备独立软件音量
- 有线与蓝牙混合场景可用
- 基于软件缓冲做基础延迟补偿

### 2.2 明确约束

- 不依赖设备是否支持硬件音量
- 不依赖系统 aggregate device 的音量控制能力
- 不要求所有蓝牙组合都低延迟

## 3. 保留与废弃

### 3.1 继续保留

- 菜单栏 App 骨架
- 设备枚举与热插拔监听
- 设置持久化
- 路由状态管理
- 设备列表 UI

### 3.2 降级为实验实现

- `ProcessTapProbeService`
- `AggregateDeviceProbeService`
- `AudioCaptureProbeService`
- 当前 `AudioRoutingEngine` 中的 aggregate/hardware volume 逻辑

这些模块保留在仓库里仅用于：

- 探测系统能力
- 对比实验
- 后续调试

不再作为正式主实现。

## 4. 新音频引擎架构

新架构拆成四层：

### 4.1 Capture 层

负责从系统输出链路中获取实时 PCM。

目标模块：

- `SystemAudioCaptureSession`

职责：

- 创建 `Process Tap`
- 创建私有 capture aggregate device
- 通过 `IOProc` 持续获取 PCM
- 将 PCM 写入共享环形缓冲

### 4.2 Buffer/Mixer 层

负责缓存、分发、软件增益和延迟补偿。

目标模块：

- `AudioFrameRingBuffer`
- `AudioFrameMixer`
- `DeviceGainState`

职责：

- 保存捕获到的连续 PCM 帧
- 为每个输出设备维护独立读指针
- 对每个设备应用：
  - 独立音量
  - 静音
  - 延迟补偿

### 4.3 Device Output 层

负责把处理后的 PCM 推到每个物理设备。

目标模块：

- `PhysicalOutputSession`

职责：

- 每个物理设备独立创建输出会话
- 每个设备独立维护输出格式、缓冲和时钟
- 在输出回调中从共享缓冲拉取音频

### 4.4 Routing Orchestration 层

负责把 UI 状态转成引擎状态。

目标模块：

- `LiveAudioRoutingEngine`
- `RoutingCoordinator`

职责：

- 创建设备输出 session
- 增删目标设备
- 更新每设备音量和静音
- 汇总引擎状态反馈给 UI

## 5. 目标主链路

```text
系统音频
  -> Process Tap
  -> Capture Aggregate Device
  -> Capture IOProc
  -> 共享环形缓冲
  -> 每设备独立读指针
  -> 软件增益 / 静音 / 延迟补偿
  -> 每物理设备独立输出会话
  -> 蓝牙耳机 / 有线耳机 / USB / HDMI
```

## 6. 为什么必须重写

### 6.1 不能再依赖硬件音量

实际验证已经证明：

- 蓝牙耳机有时支持硬件音量
- 有线耳机可能不支持
- 一旦依赖硬件音量，就无法保证“每设备独立控制”成立

### 6.2 不能再指望 AVSampleBufferAudioRenderer 扛完整方案

实验结果已经证明：

- renderer 状态可以长期停在 `unknown`
- 多物理设备同时输出不稳定
- 问题不再是小修补能稳定解决的级别

### 6.3 系统 aggregate 只能解决“合并输出”，不能解决“可控分发”

真实产品需要的是：

- 我们自己控制每个设备送什么数据
- 我们自己控制每个设备多大音量

这只能靠独立输出链路实现。

## 7. 实现阶段

### 阶段 1：收口现有工程

目标：

- 保留 UI/设备/设置层
- 把当前实验引擎标为实验实现
- 给新引擎留接口

交付：

- 新技术方案
- 稳定的工程骨架

### 阶段 2：搭建 Capture 核心

目标：

- 持续获取 PCM
- 不依赖 UI 操作反复创建销毁

交付：

- `SystemAudioCaptureSession`
- `AudioFrameRingBuffer`

### 阶段 3：搭建单设备软件输出

目标：

- 先支持 1 个物理设备
- 软件音量真正生效

交付：

- `PhysicalOutputSession`
- `AudioFrameMixer`

### 阶段 4：扩展到多设备输出

目标：

- 多设备同时稳定播放
- 每设备独立音量

交付：

- 多输出设备编排
- 每设备独立读指针

### 阶段 5：补充延迟补偿与恢复

目标：

- 有线 + 蓝牙混合场景更稳定

交付：

- 延迟补偿
- 设备断连恢复

## 8. 当前代码落地情况

当前代码已经完成第一版正式主链：

- `SystemAudioCaptureSession`
  - 负责创建 `Process Tap`
  - 创建私有 capture aggregate device
  - 通过 `IOProc` 持续抓取系统输出 PCM
- `AudioFrameRingBuffer`
  - 已从简单 chunk 数组升级为共享浮点帧缓冲
  - 支持多设备独立读指针按需读取
- `AudioFrameMixer`
  - 已支持基于 PCM 的软件增益
- `PhysicalOutputSession`
  - 已改为物理输出设备独立 `IOProc`
  - 每台设备从共享缓冲主动拉取音频
- `LiveAudioRoutingEngine`
  - 已接入 capture -> ring buffer -> 多设备输出主链

## 9. 当前行为说明

当前正式实现具备：

- 同时选择多个物理输出设备
- 每个设备独立软件音量
- 每个设备独立静音
- 不再依赖硬件音量能力

当前仍属于第一版实现，已知约束：

- 当前输出链先按设备虚拟格式直接写入，优先兼容 `Float32 PCM`
- 采样率差异先通过共享缓冲读指针插值处理
- 还没有做更完整的设备级时钟漂移补偿
- 还没有做更精细的蓝牙/有线自动延迟校准

## 10. 下一步增强项

后续继续完善的重点：

- 输出格式兼容性增强
- 非 `Float32 PCM` 设备格式适配
- 蓝牙与有线混合场景的自动延迟补偿
- 断连恢复与异常重建
- 更完整的实时统计与调试面板
- 单一物理设备软件音量输出生效
